# 09. テスト設計

## 1. 方針

- ロジックの大半を単体テストで確認し、AWS との連携は S3 のモック（moto）を使う結合テスト、主要な操作の流れは少数の E2E テストで確認する。ウィンドウの見た目やネイティブの挙動、実 AWS・実 Google での確認は手動テストで行う。
- 自動テストはすべて CI で実行する（[08-cicd.md](08-cicd.md)）。
- カバレッジの目標: `s3drive-core` は行カバレッジ 80% 以上（cargo-llvm-cov。単体テストと moto の結合テストの合計）、フロントエンドの `lib` と `features` はそれぞれ行カバレッジ 70% 以上（Vitest の v8 カバレッジ）。CI で計測し、下回ったら失敗させる（`cargo llvm-cov --fail-under-lines 80`、`vite.config.ts` の `coverage.thresholds`）。

| レベル | 対象 | ツール | 実行 |
|---|---|---|---|
| Rust 単体 | `s3drive-core` のロジック、SDK 応答の扱い | cargo test、aws-smithy-mocks | CI（Linux） |
| Rust 結合 | S3 操作の一連の流れ、SQLite | cargo test、moto | CI（Linux） |
| フロントエンド単体・コンポーネント | 書式、状態管理、コンポーネント | Vitest 5、Testing Library、`@tauri-apps/api/mocks` | CI（Linux） |
| 画面テスト | モックバックエンドでの画面操作 | Playwright（WebKit） | CI（Linux。Playwright の公式イメージ） |
| ビジュアル回帰 | 主要画面のライト／ダーク | Playwright のスクリーンショット比較 | CI（Linux。Playwright の公式イメージ） |
| ベンチマーク | 100 万件の検索 | criterion | 手元（§5） |
| E2E | 実アプリでの主要な流れ | WebdriverIO + `@wdio/tauri-service` | 毎晩（macOS） |
| 手動 | ネイティブの見た目・実 AWS・実 Google・配布物 | チェックリスト | リリース前 |

## 2. テストレベル別の内容

### 2.1 Rust 単体テスト

| 対象 | 主な確認内容 |
|---|---|
| `util::key` | NFC 正規化（NFD のファイル名）、キーの検証（1,024 バイト、制御文字）、親プレフィックスと名前の取り出し、「name (1).ext」の連番 |
| `transfer::multipart` | パートサイズの計算（8 MiB、10,000 パートを超える場合、50 TB）、マルチパートにする境界（10 進の MB） |
| `transfer`（転送キュー） | 転送がなくなるまでの待機（アップデートを転送の完了後に適用する場合。[08 §7](08-cicd.md#7-自動更新)） |
| `objects` | 移動先のキーの計算、自身の配下への移動の禁止、コピー時のストレージクラス・メタデータの指定 |
| `metrics` | StorageType からクラスへの集計、使用タイプの分類、当月・前月同期間の期間計算（月末の違い、UTC） |
| `auth` | state・nonce の照合、ID トークンのクレーム検証（テスト用の HS256 の鍵で署名したトークン。`aud`・`iss`・`nonce`・`exp` の猶予・`email_verified`）、許可リスト |
| `aws::error_map::classify` | AWS のエラーから `AppError` への変換（[05 §5](05-backend-ipc.md#5-エラーコード)） |
| SDK 応答の扱い（aws-smithy-mocks） | `ListObjectsV2` のページングとキーの復元、`DeleteObjects` の一部失敗、`HeadBucket` の 301 によるリージョン補正、`ExpiredToken` での認証情報の取り直しと 1 回だけの再試行、アップロードの `AccessDenied` でのジョブの停止、ダウンロード中の置き換え（412）での 1 回のやり直し、保存先の外を指すキーの除外、5 GB を超えるマルチパートコピー、Cost Explorer・CloudWatch・Price List の応答。`ListObjectVersions` のキー完全一致の絞り込みは結合テスト（§2.2）で確認する |

### 2.2 Rust 結合テスト（moto）

- moto を Docker で起動し（ローカルは `docker-compose.test.yml`、CI はサービスコンテナ）、`S3DRIVE_TEST_ENDPOINT` で接続先を上書きする。認証情報はダミーを使う。
- テストごとに一意の名前のバケットを作り、必要に応じてバージョニングを有効にする。
- SDK の既定のチェックサム計算に moto が対応していない場合は、テスト時だけ `request_checksum_calculation` を「必要な場合のみ」に設定する。

| シナリオ | 確認内容 |
|---|---|
| 一覧 | 区切り文字によるフォルダ、2,500 件のページング、フォルダマーカーの除外、URL エンコードされたキー（空白、日本語） |
| アップロード | 単一 PUT、マルチパート（境界値）、キャンセル時の `AbortMultipartUpload`、メタデータの付与 |
| ダウンロード | 単一・範囲指定、フォルダの階層、更新日時の復元 |
| 削除 | 削除マーカー、全バージョン削除、バージョニングなし、1,500 件のフォルダ（2 回に分割） |
| フォルダ | 作成、配下を含む移動、名前の変更、メタデータ・クラスの引き継ぎ |
| ストレージクラス | 同じキーへのコピーによる変更、同じクラスのスキップ |
| 取り出し | `RestoreObject` と状態の確認 |
| バージョン | 一覧、以前のバージョンの復元、バージョンの削除、削除マーカーの除去による復元 |
| 検索 | インデックスの作成、世代による削除の反映、各フィルタ、操作後の即時反映 |

CloudWatch の S3 日次メトリクス、Cost Explorer、Price List は moto では再現できないため、aws-smithy-mocks による単体テストで確認する。ダウンロード中の置き換え（`If-Match`）は moto では時機を合わせられないため、同じく単体テストで確認する（§2.1）。

### 2.3 フロントエンド単体・コンポーネントテスト

- Vitest 5 と Testing Library（jsdom）で実行する。グローバル API は使わず、`vitest` から明示的にインポートする（TypeScript 7 の `types` の既定が空になったため。[01 §8.3](01-architecture.md#83-typescript-7-の設定)）。IPC は `@tauri-apps/api/mocks` の `mockIPC` でモックバックエンド（§2.4）に置き換え、テストごとに `clearMocks` する。
- 画面の描画と共通の準備は `src/test/harness.tsx` にまとめる。失敗・読み込み中の表示は、モックの `failNext`・`holdNext` で再現する。

| 対象 | 主な確認内容 |
|---|---|
| `lib/format` | サイズ（10 進）、日時、金額（1 ドル未満は小数 3 桁、0.001 ドル未満は有効数字 2 桁）、割合 |
| `lib/file-kind`、`lib/storage-class` | 拡張子と種別・表示名の対応、クラスの表示名 |
| ストア | 選択（クリック、⌘、⇧、⌘A）、戻る／進む、フィルタから検索条件への変換 |
| ダイアログ | 新規フォルダ・名前変更の検証、削除ダイアログの文言（バージョニングの有無と全バージョン削除）、クラス変更ボタンの無効条件、移動先の選択不可の条件 |
| コンポーネント | ファイル一覧の状態（読み込み中・空・検索結果なし・失敗）、インスペクタの 4 つの表示、トーストの種類 |

### 2.4 モックバックエンドでの画面テスト

- `src/lib/ipc/mock/` に IPC コマンドのメモリ実装を用意する。データは DS のモックデータ（`DS: ui_kits/s3-drive/data.js`: 2 つのバケット、バージョン、コスト）に合わせる。
- `pnpm dev:mock` で、Tauri なしにブラウザで画面を動かせるようにする（UI の開発にも使う）。
- Playwright（WebKit）で、フォルダの移動、選択、コンテキストメニュー、ダイアログ、キーボードショートカット、ウィンドウ幅の切り替え（1,100px／900px）を確認する（`tests/ui/screens.spec.ts`）。
- 開発サーバーは Playwright が起動する（`playwright.config.ts` の `webServer`）。日時の表示を安定させるため、ブラウザの時計を DS の基準日時（2026/09/27 14:40）に固定する。

### 2.5 E2E テスト

- WebdriverIO と `@wdio/tauri-service` を使う。`@wdio/tauri-service` は E2E の実行環境への影響が大きいため、`package.json` でバージョンを固定し（2026 年 9 月時点で 1.4.0。範囲指定をしない）、更新するときは E2E テストが通ることを確認してから取り込む（Renovate の「WebdriverIO」グループ）。アプリには WebDriver サーバーを内蔵するプラグイン（`tauri-plugin-wdio-webdriver`）を組み込むが、Cargo の `e2e` 機能を有効にしたビルドに限り、リリースビルドには含めない。
- `e2e` ビルドでは、Google サインインを固定のセッションを返すテスト用の実装に置き換え、接続先は moto にする（本物の Google ログインは自動化しない）。
- ファイル選択ダイアログの代わりに、テスト用のフックで選択 ID を発行する。

| シナリオ |
|---|
| サインイン（テスト用）→ バケットに接続 → 一覧を表示 |
| ファイルをアップロード → 一覧に表示され、インスペクタにメタデータが出る |
| ダウンロード → 保存先にファイルができ、更新日時が復元される |
| 削除 → 削除済みの項目を表示 → 復元 |
| 新規フォルダを作成 → ファイルをそのフォルダへ移動 |
| ストレージクラスを変更 → 一覧のバッジが変わる |
| 拡張子で検索 → 結果が表示される |

### 2.6 ビジュアル回帰テスト

- モックバックエンドで主要な画面（SCR-01 のサインインとバケットへの接続、SCR-02、SCR-03、DLG-01 新規フォルダ・DLG-02 削除の確認・DLG-04 ストレージクラスを変更、MNU-01 コンテキストメニュー）を表示し、ライトとダークの両方でスクリーンショットを比較する（Playwright の `colorScheme`。`tests/ui/visual.spec.ts`）。
- 比較はフォントなどの描画環境に依存するため、基準画像（`tests/ui/__screenshots__/`）は CI と同じ Playwright の公式イメージ（Linux、`@playwright/test` と同じ版）で作り、CI もそのイメージで比べる。作り直す手順は docs/ope/03-test.md に記載する。
- DS の更新を取り込むとき（[02 §2](02-ui-foundation.md#2-取り込みと同期の方針)）は差分を確認してから基準画像を更新する。

### 2.7 手動テスト

| 区分 | 確認項目 |
|---|---|
| ウィンドウ | 透過タイトルバー、信号機ボタンの位置、ツールバーでのドラッグ、vibrancy（アクティブ／非アクティブ）、フルスクリーン、最小サイズ |
| 外観 | システム設定のライト／ダーク切り替えに再起動なしで追従する。手動指定（ライト／ダーク）でウィンドウの外観も揃う |
| カーソル・選択 | ボタン・行・メニュー上で矢印カーソル。選択できるのは入力欄とインスペクタの値だけ |
| Finder との連携 | ファイル・フォルダ・大量ファイルのドロップ、「Finder に表示」 |
| 転送 | 10 GB 級のアップロード・ダウンロードの速度と進捗、キャンセル、ネットワーク切断からの復帰、転送中の終了 |
| Google | 本物のサインイン、許可リスト、サインアウト、トークン失効後の再サインイン |
| 実 AWS | 検証用アカウントでの CloudWatch・Cost Explorer・Price List、AssumeRole、SSE-KMS、アーカイブの取り出し |
| アクセシビリティ | VoiceOver での全操作、キーボードだけでの主要操作、コントラスト |
| 配布 | Gatekeeper の警告なしで起動できる、前のバージョンからの自動更新 |

## 4. 機能別のテスト観点

| 機能 | 主な観点 | レベル |
|---|---|---|
| ユーザ認証 | 成功、キャンセル、タイムアウト、state の不一致、許可リスト外、起動時の復元、`invalid_grant`、サインアウト時のトークン取り消し | 単体・手動 |
| バケット接続 | 無効なキー、ルートユーザーのキーの拒否、AssumeRole の拒否、リージョンの自動補正、バケットがない・権限がない、バージョニング状態が不明 | 単体・結合・手動 |
| 一覧 | ページング、フォルダ、マーカーの除外、隠しファイル、特殊文字のキー、自然順の並べ替え、10 万件の表示性能 | 結合・単体・性能 |
| アップロード | 境界サイズ、パートサイズ、NFC 正規化、同名の項目の扱い（置き換え・スキップ・両方残す）、除外、キャンセル、送信中の変更、リトライ | 単体・結合・E2E |
| ダウンロード | 単一・範囲指定、途中の置き換え、連番での保存、更新日時の復元、フォルダの階層、アーカイブ、空き容量不足 | 単体・結合 |
| 削除 | 削除マーカー／全バージョン／バージョニングなし、1,000 件を超えるフォルダ、一部失敗 | 結合 |
| フォルダ管理 | 名前の検証、重複、配下を含む移動、自身の配下への移動の禁止、名前の変更、メタデータ・クラスの引き継ぎ、5 GB 超のコピー | 単体・結合 |
| ストレージクラス | 変更、同じクラスのスキップ、アーカイブの除外、注意書きの表示条件 | 単体・結合 |
| アーカイブの取り出し | 速度と日数、取り出し中、完了の検知と通知 | 単体・結合・手動 |
| メタデータ | 作成日の 3 つの規則、暗号化の表示、ユーザー定義メタデータ | 単体・結合 |
| 検索 | 作成と世代管理、各フィルタ、正規化（全角・大文字）、2 文字以下の検索、フォルダ名の一致、操作後の反映、100 万件の性能 | 単体・結合・性能 |
| バージョン管理 | キー完全一致の絞り込み、復元、削除、削除マーカーの除去、MFA Delete のエラー | 結合 |
| 利用容量 | StorageType の集計、インデックスへの切り替え、データなし | 単体 |
| コスト | 期間の計算（月末・UTC）、前月同期間、使用タイプの分類、タグ条件、予測なし、Cost Explorer の無効化、「更新」を押すまで Cost Explorer を呼ばないこと（起動時・画面表示時に `cost_refresh` が呼ばれない）、前回の結果がある場合の「更新」の失敗の表示 | 単体・コンポーネント |
| 転送管理 | 並列数の制限、状態遷移、キャンセル、終了時の確認、転送中のサインアウト・アップデートの適用の確認、転送がなくなるまでの待機 | 単体・コンポーネント・E2E |
| UI | ショートカット、コンテキストメニュー、文言（DS の規則）、幅による切り替え、ダークモード | コンポーネント・ビジュアル・手動 |
| セキュリティ | パス文字列を受け付けないこと、設定ウィンドウから許可外のコマンドを呼べないこと、ログに秘密情報が出ないこと（ログの検査）、CSP | 単体・結合・手動 |

## 5. 非機能テスト

| 観点 | 方法 | 目標（[README §8](README.md#8-非機能要件)） |
|---|---|---|
| 一覧の描画 | 10 万件のモックデータで Playwright のパフォーマンス計測 | スクロールが滑らか |
| 検索 | `s3drive-core` のベンチマーク（criterion。`cargo bench -p s3drive-core --features bench --bench search`）で 100 万件。名前（3 文字以上・2 文字以下）、名前と拡張子、種類・サイズ・期間、ストレージクラスで測る | 300 ms 以内 |
| 起動時間 | サインイン済み・キャッシュありで計測 | 2 秒以内 |
| 転送 | 実 S3 で 10 GB を転送し、速度とメモリ使用量を計測 | 帯域を使い切る、メモリが増え続けない |

## 6. リリース判定

次をすべて満たしたらリリースする。

- リリースするコミットで CI がすべて成功している。
- 同じコミットで E2E テストが成功している。
- 手動テスト（§2.7）のチェックリストを完了している。
- 未解決の重大な不具合がない。
- 署名の検証と構成証明の作成（[08 §4](08-cicd.md#4-releaseyml)）に成功している。
- クリーンな Mac で、利用者向けの手順（[08 §6.1](08-cicd.md#61-利用者のインストール手順リリースノートに記載する)）どおりに初回起動できる。
- 前のバージョンからの自動更新を確認している。
